# Лабораторная работа №3
# Упаковка FastAPI приложения в Docker, работа с источниками данных и очереди

## Цель работы

Цель лабораторной работы — упаковать FastAPI-приложение в Docker, интегрировать парсер данных с базой данных PostgreSQL, реализовать вызов парсера через HTTP API, а также добавить асинхронную обработку задач через очередь Celery и Redis.

---

# 1. Исходное приложение

В качестве основного приложения использовался сервис Travel Buddy, разработанный в лабораторной работе №1. Приложение реализовано на FastAPI и предназначено для поиска попутчиков для путешествий.

В проекте уже были реализованы:

- модели пользователей;
- модели поездок;
- направления путешествий;
- навыки и интересы пользователей;
- участники поездок;
- подключение к PostgreSQL через SQLAlchemy;
- миграции Alembic;
- REST API.

---

# 2. Упаковка FastAPI приложения в Docker

Для основного приложения был создан `Dockerfile`. В нем используется базовый образ `python:3.13-slim`. В контейнер копируются зависимости из `requirements.txt`, после чего устанавливаются необходимые библиотеки и запускается FastAPI-приложение через `uvicorn`.

Основной контейнер приложения запускается на порту `8000`.

---

# 3. Подключение PostgreSQL через Docker Compose

Для базы данных используется контейнер PostgreSQL. В `docker-compose.yml` описан сервис `db`, для которого указаны:

- имя базы данных `travel_buddy_db`;
- пользователь `postgres`;
- пароль `postgres`;
- порт `5432`;
- volume для сохранения данных;
- healthcheck для проверки готовности базы данных.

После запуска контейнеров основное приложение выполняет команду:

```bash
alembic upgrade head
```

Это позволяет автоматически применить миграции и подготовить структуру базы данных.

---

# 4. Отдельный сервис парсера

Для парсинга веб-страниц был создан отдельный сервис `parser_service`. Это отдельное FastAPI-приложение, которое запускается в собственном контейнере на порту `8001`.

Сервис имеет эндпоинт:

```http
POST /parse
```

Он принимает URL, загружает HTML-страницу, получает содержимое тега `title` и сохраняет результат в таблицу `trips` базы данных PostgreSQL.

Пример результата:

```json
{
  "trip_id": 1,
  "title": "Example Domain",
  "url": "https://example.com",
  "message": "Parsing completed by parser_service"
}
```

---

# 5. Вызов парсера из основного FastAPI приложения

В основном FastAPI-приложении был добавлен роутер `parser`. Он содержит эндпоинт:

```http
POST /parser/parse
```

Этот эндпоинт принимает URL от клиента, отправляет HTTP-запрос в отдельный контейнер `parser_service`, получает результат парсинга и возвращает его клиенту.

Таким образом, основное приложение не выполняет парсинг напрямую, а делегирует эту задачу отдельному сервису. Это разделяет ответственность между компонентами системы.

---

# 6. Очередь задач Celery + Redis

Для получения 100% за лабораторную работу была реализована обработка парсинга через очередь.

В проект были добавлены сервисы:

- `redis` — брокер сообщений и хранилище результатов;
- `celery_worker` — обработчик фоновых задач;
- `celery_beat` — сервис периодических задач.

В основном приложении добавлен эндпоинт:

```http
POST /parser/parse-async
```

Он не выполняет парсинг сразу, а ставит задачу в очередь Celery и возвращает пользователю `task_id`.

Пример ответа:

```json
{
  "message": "Parsing task has been added to queue",
  "task_id": "...",
  "status": "PENDING"
}
```

Для проверки статуса задачи добавлен эндпоинт:

```http
GET /parser/tasks/{task_id}
```

Если задача выполнена успешно, эндпоинт возвращает результат парсинга.

---

# 7. Периодические задачи

Также была настроена периодическая задача Celery Beat. Она раз в час вызывает задачу парсинга страницы `https://example.com`.

Это показывает, что Celery может использоваться не только для обработки задач по запросу пользователя, но и для регулярного выполнения фоновых операций.

---

# 8. Docker Compose

В `docker-compose.yml` описаны следующие сервисы:

| Сервис | Назначение | Порт |
|---|---|---|
| `app` | основное FastAPI-приложение | `8000` |
| `parser_service` | отдельный сервис парсера | `8001` |
| `db` | PostgreSQL | `5432` |
| `redis` | брокер Celery | `6379` |
| `celery_worker` | обработчик задач | - |
| `celery_beat` | периодические задачи | - |

Запуск всех сервисов выполняется одной командой:

```bash
docker compose up --build
```

# 10. Вывод

В ходе лабораторной работы FastAPI-приложение было упаковано в Docker и запущено вместе с PostgreSQL через Docker Compose.

Парсер данных был вынесен в отдельный сервис, что позволило разделить ответственность между основным API и компонентом парсинга.

Также была реализована асинхронная обработка задач через Celery и Redis. Такой подход позволяет запускать долгие операции в фоне и не блокировать основной HTTP-запрос.

В результате были выполнены все три подзадачи лабораторной работы, включая работу с Docker, вызов парсера через HTTP и обработку парсинга через очередь задач.
